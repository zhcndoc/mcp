MCP 协议即将迎来自发布以来最大的一次修订。正如你可能已经从
[我们最近的候选版公告](/posts/2026-07-28-release-candidate/)中看到的那样，新的
协议修订将转为无状态，移除 `initialize` 握手和协议级
会话，并完成我们在
[The Future of MCP Transports](/posts/2025-12-19-mcp-transport-future/) 中制定的计划。如果你正在构建 MCP
服务器，现在可以使用简单的轮询负载均衡器对其进行扩展，无需再
管理粘性会话或存储共享会话。对于客户端开发者来说，像
[Multi Round-Trip Requests (MRTR)](https://modelcontextprotocol.io/specification/draft/basic/patterns/mrtr)
这样的新模式将为服务器到客户端的交互开启全新的可能性。你可以查看
[完整更新日志](https://modelcontextprotocol.io/specification/draft/changelog) 来了解
即将到来的变化。

从今天开始，你可以使用全部四个
[Tier 1](https://modelcontextprotocol.io/community/sdk-tiers) SDK 来测试协议即将推出的所有更新，这些 SDK 分别由
[Python](https://github.com/modelcontextprotocol/python-sdk) v2 和
[TypeScript](https://github.com/modelcontextprotocol/typescript-sdk) v2 领衔，同时
[Go](https://github.com/modelcontextprotocol/go-sdk) 和
[C#](https://github.com/modelcontextprotocol/csharp-sdk) 的 beta 版也已提供。我们鼓励你
使用 beta SDK 在真实工作负载上进行测试，并在我们逐步接近
正式规范修订时告诉我们哪些地方会出问题。新的协议规范将于 2026 年 7 月 28 日发布。

![三层结构：底层是 MCP 规范，中间是 SDK（Python、TypeScript、Go、C# 等），顶层是基于其构建的客户端和服务器。](/posts/images/sdk-betas/stack.svg)

## 您现有的服务器仍然可以正常工作

首先，我们想向您保证，对于现有客户端和服务器来说，今天不会有任何中断，7 月 28 日也不会有任何中断。这只是规范性说明文本发布的日期，并不是对依赖当前协议版本的任何实现者的停用时间。

SDK 测试版的存在，是为了让您在新规范最终确定之前测试协议变更并向我们提供反馈。对于任何关键工作负载，稳定版 SDK 仍然是推荐版本。

您可能已经看到，一些 SDK（例如 Python 和 TypeScript）也切换到了 v2。这些都是新的主版本，因此将您自己的代码迁移到它们上面属于破坏性变更，而且您可以按照自己的计划进行；这与 7 月 28 日发生的任何事情都无关。v2 发布后，TypeScript SDK 至少在六个月内将继续提供 v1.x 的 bug 修复和安全更新，而 Python v1.x 分支也将继续接收关键 bug 修复和安全补丁。

尝试测试版是安全的，因为每一步都是自愿选择的。安装 Python、Go 或 C# SDK 时，如果没有明确请求预发布版本，默认仍会解析为稳定版本；TypeScript v2 包是全新的包名，目前还没有稳定发布版，因此安装它们本身就是自愿选择。在 TypeScript 和 Go SDK 中，这种自愿选择还延伸到了传输层：升级本身不会改变您的服务器通过 HTTP 发送的内容。提供 `2026-07-28` 是您在配置传输时做出的明确选择。Python 或 C# 服务器则会在升级时直接采用新的修订版：Python v2 服务器会通过同一个端点同时响应两个协议修订版，而 C# 预览版的 HTTP 传输默认使用新的无状态模式。并且，使用 `2026-07-28` 的客户端在连接到 `2025-11-25` 或更早版本的服务器时，会回退到 `initialize` 握手，因此旧服务器和新客户端仍然可以互操作。

如果您想确保自己的用户不会受到影响：

- 如果您发布的是依赖 Python `mcp` 包的库，请立即添加上限约束（例如 `mcp>=1.27,<2`），这样稳定版 v2 发布时就不会让您的用户感到意外。
- 当您测试测试版时，请固定到精确版本。公共 API 在测试版与稳定版之间仍可能发生变化。

## Beta SDK 实现了什么

所有四个 beta 版本都实现了来自 release candidate 的核心协议变更，
每个版本的说明都详细列出了所涵盖的变更。[RC 公告](/posts/2026-07-28-release-candidate/)对这些变更
进行了深入说明，不过如果你只想看简短版本：

- **无状态核心**
  ([SEP-2575](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2575),
  [SEP-2567](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2567)).
  每个请求都是自描述的，能力来自
  `server/discover`，并且任何服务器实例都可以处理任何请求。
- **多轮往返请求（MRTR）**
  ([SEP-2322](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2322)).
  工具可以返回 `InputRequiredResult` 在调用过程中向用户询问内容，
  客户端随后带着答案重试。不需要长生命周期流！
- **可路由的传输头**
  ([SEP-2243](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2243)).
  `Mcp-Method` 会出现在每个请求上，而 `Mcp-Name` 会出现在那些命名了
  工具、资源或提示的请求上，这样网关和限流器就可以在不解析正文的情况下进行路由。
- **授权加固**，包括根据
  [RFC 9207](https://www.rfc-editor.org/rfc/rfc9207)
  进行 `iss` 验证
  ([SEP-2468](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2468))，
  动态客户端注册中的 `application_type`
  ([SEP-837](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/837))，
  step-up 时的 scope 累积
  ([SEP-2350](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2350))，
  以及凭证与签发该凭证的授权服务器进行绑定
  ([SEP-2352](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2352))。
  `application_type` 这一变更是桌面端和 CLI 客户端最能感受到的：
  授权服务器不再默认把它们设为 `"web"`，也不会再拒绝它们的 `localhost` 重定向。
- **标准错误码**
  ([SEP-2164](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2164))。
  缺失的资源现在返回 JSON-RPC `-32602`，而不是
  MCP 自定义的 `-32002`。如果你的客户端是按字面值匹配的，你应该更新
  它。
- **弃用标注**
  ([SEP-2577](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2577))
  针对 roots、sampling 和 logging。这只是建议性质，因为这些已弃用的方法、
  类型和能力标志在本版本以及其发布后一年内的每个规范版本中仍然可用。

完整的协议文本位于
[草案规范](https://modelcontextprotocol.io/specification/draft)中，
而
[changelog](https://modelcontextprotocol.io/specification/draft/changelog)
列出了相对于 `2025-11-25` 的每一项变更。

## Python: `mcp` v2

v2 这一版本对你已经熟悉的包进行了重构：`FastMCP` 变为
`MCPServer`，装饰器 API 也沿用下来。一个完整的服务器仍然
像这样：

```python
from mcp.server import MCPServer

mcp = MCPServer("Demo")


@mcp.tool()
def add(a: int, b: int) -> int:
    """相加两个数字。"""
    return a + b


@mcp.resource("greeting://{name}")
def greeting(name: str) -> str:
    """按名字问候某人。"""
    return f"Hello, {name}!"
```

和 v1 一样，你不需要编写 JSON Schema，因为会直接采用惯用的 Python 构造。
请使用精确版本号安装 beta 版，因为未固定版本的安装仍会停留在 v1.x：

```bash
uv add "mcp[cli]==2.0.0b1"
# 或者
pip install "mcp[cli]==2.0.0b1"
```

如果你现在已经有一个 v1 服务器，
[迁移指南](https://py.sdk.modelcontextprotocol.io/v2/migration/)
会逐一讲解每个破坏性变更。

在协议层面，这个 beta 版本端到端支持 `2026-07-28`：服务器会
响应新的 `server/discover` 方法，而客户端的默认模式会先探测它，
并在旧服务器上回退到 `initialize`。升级服务器不会让现有客户端失联：
v2 服务器会同时响应旧的 `initialize` 握手和 `server/discover`，
因此使用 `2025-11-25` 的客户端仍然可以连接。你可以在进程内测试这一切：
直接将你的 `MCPServer` 实例传给 `Client`
（`async with Client(mcp) as client:`），它会以内存方式连接，模式与 FastAPI 的 `TestClient` 相同。
无需子进程，也不需要端口。
[SDK 文档](https://py.sdk.modelcontextprotocol.io/v2/)提供了教程和完整的
API 参考。

## TypeScript：拆分包

TypeScript v2 不再使用单体的 `@modelcontextprotocol/sdk` 包，而是改为使用更聚焦的包，例如用于服务器的 `@modelcontextprotocol/server`、用于客户端的 `@modelcontextprotocol/client`，以及面向 Node.js、Express、Hono 和 Fastify 的轻量适配器。它仅支持 ESM，并可在 Node.js 20+、Bun 和 Deno 上运行。工具 schema 现在使用
[Standard Schema](https://standardschema.dev/)，因此你可以使用 Zod v4、Valibot、ArkType，或任何兼容的库。

你可以像这样引导一个最小服务器：

```typescript
import { McpServer } from "@modelcontextprotocol/server";
import { StdioServerTransport } from "@modelcontextprotocol/server/stdio";
import * as z from "zod/v4";

const server = new McpServer({ name: "greeting-server", version: "1.0.0" });

server.registerTool(
  "greet",
  {
    description: "向某人致以问候",
    inputSchema: z.object({ name: z.string() }),
  },
  async ({ name }) => ({
    content: [{ type: "text", text: `Hello, ${name}!` }],
  }),
);

async function main() {
  const transport = new StdioServerTransport();
  await server.connect(transport);
}

main();
```

要安装这些包中的任何一个，你可以使用现在熟悉的 `npm` 命令：

```bash
npm install @modelcontextprotocol/server@beta
npm install @modelcontextprotocol/client@beta
```

对于 HTTP 部署——这正是无状态协议发挥优势的地方——`createMcpHandler`（来自
`@modelcontextprotocol/server`）是入口点。它会为每个请求提供
`2026-07-28`，并通过同一个端点处理来自
`2025-11-25` 的流量，同时由适配器包将其连接到 Node.js、Express、Hono 和 Fastify。

从 v1 迁移大多是机械性的，并且有一个 codemod 会替你完成那些枯燥的部分，
包括将 `.tool()` 重命名为
`registerTool` 以及错误类型的重命名。你可以通过以下方式获取它：

```bash
npx @modelcontextprotocol/codemod@beta v1-to-v2 .
```

该仓库提供了两个指南，会在整个过程中帮助你：

- [从 v1 升级到 v2](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/migration/upgrade-to-v2.md)
- [采用 2026-07-28 修订版](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/migration/support-2026-07-28.md)

虽然这看起来可能有些令人困惑，但这两个都是独立的步骤——你现在就可以迁移到 v2，
并在准备好时再启用新的协议修订版。[v2 API 文档](https://ts.sdk.modelcontextprotocol.io/v2/)涵盖了
其余内容。

## Go 和 C#

Go 和 C# 的 beta 版本走的是一条稍微更平缓的路径——没有包拆分，也不会重构你日常使用的 API。

Go SDK 会在 `v1.7.0-pre.1` 中提供对 `2026-07-28` 的支持，且模块路径与你当前已经在使用的版本相同：

```bash
go get github.com/modelcontextprotocol/go-sdk@v1.7.0-pre.1
```

通过 HTTP 提供新修订版，与 TypeScript 中一样，都是一个显式选择：只有当你设置 `StreamableHTTPOptions.Stateless = true` 时，可流式 HTTP 传输才会接受 `2026-07-28`。如果保持不设置，客户端会协商降级到 `2025-11-25`。  
[发布说明](https://github.com/modelcontextprotocol/go-sdk/releases/tag/v1.7.0-pre.1) 会逐一讲解每项协议变更，而 [SDK 文档](https://go.sdk.modelcontextprotocol.io) 将覆盖更新后的 API。

C# beta 则作为 `ModelContextProtocol` 包的 `2.0.0-preview.1` 版本发布：

```bash
dotnet add package ModelContextProtocol --prerelease
```

稳定的 v1.x API 在 v2 中仍然可用。破坏性变更仅限于规范已弃用的能力（roots、sampling 和 logging），这些内容会标记为 `[Obsolete]`，并指向其替代方案；此外还包括那些在规范逐步定型过程中其契约发生变化的实验性 API。  
[预览版发布说明](https://github.com/modelcontextprotocol/csharp-sdk/releases/tag/v2.0.0-preview.1) 包含按每个 SEP 列出的实现表，而 [SDK 文档](https://csharp.sdk.modelcontextprotocol.io) 会在包稳定后提供更新后的 API 参考。

## 给我们你的反馈

距离规范最终定稿只剩四周了。我们需要你的帮助，让发布过程更顺利！

1. 在你的服务器的一个分支中安装一个 beta 版本，并让真实流量跑在它上面，而不只是测试“理想路径”。
2. 如果你是在网关或负载均衡器后面运行，请提供无状态路径，看看你的路由是否仍然需要协议不再提供的任何内容。在 TypeScript 中，该路径是 `createMcpHandler`；在 Go 中，设置 `StreamableHTTPOptions.Stateless = true`；在 Python 中，v2 HTTP 应用会从一个端点同时响应这两个协议修订版。
3. 把你发现的问题提交出来。SDK 相关问题请提交到你正在使用的 SDK 的 issue tracker：
   - [Python](https://github.com/modelcontextprotocol/python-sdk/issues)
   - [TypeScript](https://github.com/modelcontextprotocol/typescript-sdk/issues)
   - [Go](https://github.com/modelcontextprotocol/go-sdk/issues)
   - [C#](https://github.com/modelcontextprotocol/csharp-sdk/issues)

   如果你发现的是协议本身的问题，请前往 [规范仓库](https://github.com/modelcontextprotocol/modelcontextprotocol/issues)。

值得注意的是，公共 API 在 beta 版本与稳定版之间仍可能发生变化，因此请锁定精确版本。接下来四周里的反馈，将成为他们构建后续版本的基础。如果你还有其他反馈，或者想与 SDK 维护者交流，请加入我们的 [贡献者 Discord](https://modelcontextprotocol.io/community/communication#discord)。

我们很期待看到你会构建出什么！
