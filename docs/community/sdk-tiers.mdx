此页面定义了三个 SDK 层、每个层的要求、SDK 如何在它们之间移动以及 SDK 存储库必须使用的问题标签。这些层已被规范增强提案 (SEP) [SEP-1730](/seps/1730) 采用，并由流程 SEP 进行更改。 [SDK 工作组](/community/working-groups/sdk) 负责运营它们，每个 SDK 的当前层级显示在 [SDK 页面](/docs/sdk) 上。

<a id="tier-requirements" />
## 等级要求

第 1 层 SDK 得到完全支持并实现所有非实验功能，包括采样和启发等可选功能。第 2 层中的 SDK 得到积极维护，并致力于提供完整的规范支持，第 3 层中的 SDK 处于实验性、部分实现或专门化阶段。任何层都不需要实验性功能和协议扩展（例如任务和 MCP 应用程序）。
| 要求                 | Tier 1：完全支持                                                                  | Tier 2：承诺完全支持                               | Tier 3：实验性   |
| --------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------- | ---------------------- |
| **一致性测试**       | 100% 通过率                                                                           | 80% 通过率                                                    | 无最低要求             |
| **新协议特性**   | 在新规范版本发布之前，根据特性复杂度按版本商定时间表 | 6 个月内                                                  | 无时间表承诺 |
| **问题分类**            | 2 个工作日内                                                                   | 一个月内                                                   | 无要求         |
| **严重缺陷解决** | 7 天内                                                                            | 两周内                                                 | 无要求         |
| **稳定版本发布**          | 需要清晰的版本控制                                                           | 至少一个稳定版本                                      | 不需要           |
| **文档**           | 全面，包含所有功能的示例                                             | 涵盖核心功能的基本文档                       | 无最低要求             |
| **依赖策略**       | 已发布的更新策略                                                                  | 已发布的更新策略                                          | 不需要           |
| **路线图**                 | 已发布的路线图                                                                        | 已发布的向 Tier 1 推进的计划或保留在 Tier 2 的说明 | 不需要           |

**问题分类**意味着标记问题并确定其是否有效，而不是解决它。

**严重错误** 是指[优先级标签](#priority-only-if-actionable) 下定义的 `P0` 问题。

**稳定版本** 是指明确标记为生产就绪的已发布版本，例如版本 `1.0.0` 或更高版本，没有预发布标识符，例如 `-alpha`、`-beta` 或 `-rc`。

**清晰的版本控制**意味着遵循惯用的版本控制模式并记录重大更改策略。

**路线图**是指一组已发布的具体步骤和工作项，用于跟踪所需规范组件的实施（非实验性功能和可选功能，如[一致性测试](#conformance-testing) 范围内）。

<a id="conformance-testing" />
## 一致性测试

一致性通过[一致性测试套件](https://github.com/modelcontextprotocol/conformance) 进行测量。每个官方 SDK 都会针对其默认分支运行套件并发布结果。

矩阵中的通过率仅根据适用的所需测试计算：
- 针对 SDK 目标规范版本的测试
- 排除标记为 pending 或 skipped 的测试
- 排除实验性功能测试
- 排除旧版向后兼容性测试（除非 SDK 声称支持旧版）
- 排除在一致性仓库中标记为 `disputed` 的测试，直至争议解决

持续的测试失败将在 [Tier delegation](#tier-relegation) 下处理。

<a id="tier-advancement" />
## 等级提升

要请求更高级别，SDK 维护者：
1. 根据[等级要求](#tier-requirements) 自我评估 SDK。
2. 在 [modelcontextprotocol/modelcontextprotocol](https://github.com/modelcontextprotocol/modelcontextprotocol) 存储库中提出问题并提供支持证据。
3. 通过最新稳定版本上所请求层的一致性阈值。
4.获得SDK工作组的批准。

SDK 工作组进行最终的层级分配，并按照其[章程](/community/working-groups/sdk) 中的规定记录决定和理由。

<a id="tier-relegation" />
## 降级级别

如果最新稳定版本的现有一致性测试连续 4 周失败，则 SDK 可能会被移至较低层：
- **第 1 层到第 2 层**：任何一致性测试均失败。
- **第 2 层到第 3 层**：超过 20% 的一致性测试失败。
如果问题两个月内仍未得到处理，SDK 也可能会被降级。

SDK 工作组同样可能会降级始终未能按照[第 1 层 SDK 义务](/community/feature-lifecycle#tier-1-sdk-obligations) 的要求公开规范弃用的第 1 层 SDK。小组决定每次降级并记录降级的理由。

<a id="issue-triage-labels" />
## 发布分类标签

SDK 存储库必须使用以下标签。根据它们计算出两层指标：分类响应时间（问题创建到第一个标签）和关键错误解决时间（`P0` 标签到关闭）。

<a id="type-pick-one" />
### 类型（选一个）

| 标签         | 描述                   |
| ------------- | ----------------------------- |
| `bug`         | 某些功能无法工作       |
| `enhancement` | 请求新功能       |
| `question`    | 请求更多信息 |

使用 [GitHub 的本机问题类型](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/managing-issue-types-in-an-organization) 的存储库无需类型标签即可满足此要求。

<a id="status-pick-one" />
### 状态（选一个）

在每个存储库中使用这些确切的标签名称。
| 标签                | 描述                                             |
| -------------------- | ------------------------------------------------------- |
| `needs confirmation` | 不清楚是否仍然相关                               |
| `needs repro`        | 信息不足以复现                   |
| `ready for work`     | 已有足够信息可以开始                         |
| `good first issue`   | 适合新人                                      |
| `help wanted`       | 欢迎熟悉代码库的人士贡献 |

<a id="priority-only-if-actionable" />
### 优先级（仅当可操作时）

| 标签 | 描述                                                     |
| ----- | --------------------------------------------------------------- |
| `P0`  | 严重：核心功能故障或高严重性安全 |
| `P1`  | 影响许多用户的重大缺陷                            |
| `P2`  | 中等问题，有价值的功能请求                      |
| `P3`  | 锦上添花，罕见的边缘情况                                  |

`P0` 问题是：
- CVSS 评分为 7.0 或更高（高或严重严重性）的安全漏洞
- 阻止基本 MCP 操作的核心功能故障：连接建立、消息交换或核心原语（工具、资源、提示）的使用
