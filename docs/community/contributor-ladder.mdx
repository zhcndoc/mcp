本页定义 MCP 项目中的贡献者角色、各角色的要求和权限，以及角色晋升方式。本页由规范增强提案（SEP）[SEP-2148](/seps/2148)采纳，后续变更通过流程类 SEP 进行。角色间权限见[治理](/community/governance#roles)；小组级别的角色（工作组成员、工作组负责人、兴趣组召集人）见[工作组和兴趣组](/community/working-interest-groups)。

<a id="roles-at-a-glance" />
## 角色一览

| 角色 | 定义 | 权限 | 最短经历 |
| --- | --- | --- | --- |
| [贡献者](#contributor) | 以任何形式为 MCP 项目做出贡献的人 | 无正式权限；议题和小组会议对所有人开放。不同仓库的[拉取请求](/community/contributing#change-the-specification-or-docs)权限要求各异。 | 无 |
| [成员](#member) | 持续活跃的贡献者 | GitHub 组织成员资格和议题分流权限 | 2 至 3 个月的有效贡献 |
| [维护者](#maintainer) | 负责特定领域（SDK、工具、文档或小组）的人 | 所负责领域的合并权限；名单见 [`MAINTAINERS.md`](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/MAINTAINERS.md)。 | 担任成员至少 6 个月 |
| [核心维护者](#core-maintainer) | 负责项目整体技术方向与协议管理 | 所有仓库的管理权限 | 持续担任维护者并作出贡献后，经邀请加入 |
| [主要维护者](#lead-maintainer) | 创始人担任的治理角色 | 所有仓库和基础设施的管理权限 | 仅限创始人及其继任者 |
| [社区版主](#community-moderator) | 负责执行行为准则和处理事件 | Discord 和 GitHub Discussions 的审核工具 | 须先成为成员；与技术晋升并行 |

时间要求是最低门槛，晋升由相应审批方酌情决定。例外须经核心维护者批准并书面说明理由。代码、规范文本、文档、议题分流、安全、社区工作和审核贡献都同样重要。

<a id="contributor" />
## 贡献者

贡献者是以任何形式参与 MCP 项目的人，包括提交议题或拉取请求、参与小组讨论、撰写文档或帮助他人。此角色没有正式要求。请从[贡献指南](/community/contributing#where-to-start)开始，并加入[沟通方式](/community/communication)中列出的频道。规范仓库的拉取请求须由[成员](#member)创建；其他仓库各自规定贡献方式。

<a id="member" />
## 成员

**要求。** 对 MCP 作出多项贡献，其中至少有一项已合并的拉取请求或已被接受的贡献；持续参与 2 至 3 个月，而非一次性贡献；GitHub 帐户启用双重身份验证。提名公布后 7 天内，现有成员无人提出异议。

**提名和批准。** 由来自不同组织的两名成员或维护者提名，或由一名核心维护者或主要维护者提名。提名期内无人反对即获批准。

**职责。** 回复分配给自己的议题和拉取请求；尽可能帮助新贡献者入门；遵守[行为准则](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/CODE_OF_CONDUCT.md)。

**权限。** 获得 GitHub 组织成员资格和议题分流权限，可以分配议题和拉取请求，也可以使用 `/lgtm` 等审查命令。可以按[贡献指南](/community/contributing#change-the-specification-or-docs)在规范仓库创建拉取请求。符合资格担任工作组负责人或兴趣组召集人。成员名册维护在 [access 仓库](https://github.com/modelcontextprotocol/access)，不另行公开成员名单。

**最短经历。** 2 至 3 个月的持续有效参与。

<a id="maintainer" />
## 维护者

**要求。** 至少六个月持续担任成员并作出贡献；负责一个明确领域，例如 SDK、工具、文档、小组或重大计划；代表项目工作，而非代表任何雇主；熟悉[路线图](/development/roadmap)、[设计原则](/community/design-principles)及所负责领域的实际用法；完成安全和治理培训。

**赞助和批准。** 由一名维护者或核心维护者赞助，并由核心维护者批准。

**职责。**

- 维护所负责领域的运行质量，包括测试稳定性、文档、发布流程和里程碑规划。
- 按[升级流程](#escalation)规定的时限审查升级事项，确保提交核心维护者的提案已充分完善并考虑整个生态的影响。
- 指导成员并赞助未来的维护者。
- 代表该领域的用户发声；应要求代表 MCP 对外交流；参与路线图、治理、GitHub 和 Discord 讨论。

**权限。** 对负责领域拥有合并权限。可以赞助成员、维护者和 SEP（参阅 [SEP 指南](/community/sep-guidelines#sponsors)）。参与路线图和优先级讨论。名单见 [`MAINTAINERS.md`](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/MAINTAINERS.md)。

**最短经历。** 至少担任成员 6 个月。

<a id="core-maintainer" />
## 核心维护者

**要求。** 至少六个月担任维护者或具备同等经历；在项目级决策中展现良好判断力，并获得跨组织信任。

**提名和批准。** 由多数核心维护者提名、主要维护者批准，或由主要维护者直接任命。主要维护者可将核心维护者免职（参阅[治理](/community/governance#roles)）。

**职责。** 维护设计原则和路线图，并以长期视角审慎推动协议演进。依据[决策流程](/community/governance#decision-process)处理有争议的跨领域技术问题和治理事项。对外代表项目、规划继任安排并关注社区健康。每两周参加核心维护者会议和[指导小组](/community/governance#roles)会议。

**权限。** 对 SEP 和治理事项投票；批准维护者、重大变更和重要规范修订；拥有所有 MCP 仓库的管理权限。名单见 [`MAINTAINERS.md`](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/MAINTAINERS.md)。

**最短时间。** 在维护者持续贡献后受邀请。

核心维护者团队保持精简，并将工作授权给维护者、工作组负责人和兴趣组召集人，而非不断扩大团队规模。评估候选人时，核心维护者会考虑其成员构成是否反映 MCP 的广泛采用情况，包括在生产环境中运行 MCP 的企业。

<a id="lead-maintainer" />
## 首席维护者

主要维护者是由项目创始人终身担任的角色，没有晋升途径。主要维护者除拥有核心维护者的全部职责和权限外，还拥有[治理](/community/governance#roles)中规定的权力，包括行使否决权、任命或罢免核心维护者，以及单独作出决定。

<a id="succession" />
### 继任

如果首席维护者因任何原因离开该职位，则继任者将从其书面通知开始，或者，如果他们无法发出通知，则在剩余的首席维护者或核心维护者确定首席维护者无法继续任职时开始。

当一名或多名首席维护者留下时，如果留下一名以上，他们将通过多数票任命继任者，并继续执政，直到任命继任者为止。如果没有留下主要维护者，核心维护者将在 30 天内以多数票任命继任者，并且该项目将由核心维护者的三分之二投票运行，直到任命新的主要维护者。

<a id="community-moderator" />
## 社区管理员

**要求。** 已达到成员级别；在社区互动中保持冷静并作出审慎判断；熟悉[行为准则](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/CODE_OF_CONDUCT.md)；妥善、公平地处理敏感情况。

**赞助和批准。** 由一名核心维护者或主要维护者赞助并批准。若版主未能遵循审核标准或违反行为准则，核心维护者可以将其免职。版主可随时辞任。

**职责。**

- 关注 Discord 和 GitHub Discussions 等社区频道，发现可能违反行为准则的情况。
- 分流并回应行为准则报告，将严重或复杂事件升级给核心维护者。
- 与其他管理员协调，确保执行的一致性。
- 记录审核操作并对事件详细信息保密。
- 回避自己参与的事件；此类事件应直接交由核心维护者处理。

**权限。** 使用 Discord 和 GitHub Discussions 的审核工具，并可访问私有审核频道。可对违反行为准则的用户发出警告、禁言或临时封禁。名单见 [`MAINTAINERS.md`](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/MAINTAINERS.md#community-moderators)。

**最短经历。** 除成员级别要求外无额外时间要求。

社区版主是与其他角色并行的职责，可以与任一角色兼任，也不是技术晋升的前置条件。每个角色都应重视社区审核工作。

<a id="leading-a-working-or-interest-group" />
## 领导一个工作或兴趣小组

工作组负责人和兴趣组召集人须达到成员级别，无需先成为维护者；此类工作也可计入维护者晋升经历。具体要求、赞助和职责见[工作组和兴趣组](/community/working-interest-groups#leadership)。

<a id="advancement-process" />
## 进阶流程

你可以自荐，也可以由赞助人提名。自荐者仍须获得下列角色所要求的赞助。

1. 被提名者或赞助人使用提名模板，在[规范仓库](https://github.com/modelcontextprotocol/modelcontextprotocol)创建议题，并附上能证明符合角色要求的贡献链接。
2. 赞助人在议题中确认支持提名。
3. 开放 7 天社区意见征询期。
4. 由相应审批方作出决定，并在线程中记录结果。
5. 通过 [access 仓库](https://github.com/modelcontextprotocol/access)配置权限，新任角色持有人完成入职流程。

| 角色 | 赞助要求 | 批准方 |
| --- | --- | --- |
| 成员 | 来自不同组织的两名成员或维护者，或一名核心维护者/主要维护者 | 现有成员在 7 天内无异议 |
| 维护者 | 一名维护者或核心维护者 | 核心维护者 |
| 核心维护者 | 由多数核心维护者提名 | 主要维护者；主要维护者也可直接任命 |
| 社区版主 | 一名核心维护者或主要维护者 | 赞助人（核心维护者或主要维护者） |

<a id="escalation" />
## 升级

决策由能够处理该事项的最低级别角色作出，并以书面形式记录。维护者、工作组负责人和兴趣组召集人处理各自职责范围内的日常事务。核心维护者处理升级事项、跨领域问题，以及流程明确要求其介入的事项（例如规范变更和维护者任命）。主要维护者仅处理有争议的治理决定，或核心维护者无法达成决定的情况。只有遇到阻塞、影响项目整体范围的问题，或流程明确要求升级时，才应升级处理。

| 问题类型 | 第一级处理方 | 第二级处理方 | 响应时限 |
| --- | --- | --- | --- |
| 拉取请求中的技术分歧 | 相关领域的维护者 | 核心维护者 | 5 个工作日 |
| 工作组内的技术分歧 | 工作组负责人 | 核心维护者 | 5 个工作日 |
| 兴趣组内的技术分歧 | 兴趣组召集人 | 核心维护者 | 5 个工作日 |
| 与工作组负责人或兴趣组召集人的分歧 | 核心维护者 | 主要维护者 | 7 个工作日 |
| 对维护者决定有异议 | 核心维护者 | 主要维护者 | 7 个工作日 |
| 核心维护者之间的分歧 | 主要维护者 | 无 | 10 个工作日 |
| 行为准则违规 | 社区版主 | 核心维护者 | 立即处理 |
| 安全问题 | 核心维护者 | 主要维护者 | 立即处理 |

漏洞应首先通过私有渠道报告（参阅[报告漏洞](/community/policies#reporting-a-vulnerability)）。漏洞报告建立后，安全问题按上表在维护者之间升级。

获悉漏洞正遭利用或发生严重事件的维护者，必须遵循[欧盟《网络韧性法案》（CRA）升级规则](/community/policies#eu-cyber-resilience-act-cra-stewardship)。在处理问题的同时，须立即在 Discord 的 `#security-disclosures` 频道通知核心维护者或主要维护者；之后由核心维护者或主要维护者与 Linux Foundation 的 CRA 监管专员协作。

升级时：

1. 记录当前决定、考虑过的选项和未解决的分歧。
2. 将事项提交给相应的升级处理方，并明确说明需要其解决的问题。
3. 升级处理方给出有约束力的指导、要求补充信息，或决定进一步升级。

工作组或兴趣组内部的争议遵循[工作组和兴趣组](/community/working-interest-groups#escalation)页面的流程。该页面列出了须直接提交核心维护者的争议，并要求负责处理小组争议的核心维护者与相关各方不存在组织从属关系。

<a id="inactivity-stepping-down-and-removal" />
## 不活跃、下台和撤职

<a id="inactivity" />
### 不活动

连续 3 个月没有缴款的会员可能会转为退休会员。返回的会员将经历一个简单的重新熟悉过程。 6个月内没有贡献的维护者在核心维护者审核后可能会被转为退休状态，并且此举会撤销他们的合并权利。返回的维护人员重复安全和治理入门。首席维护者在 6 个月没有参与治理或技术决策的情况下对核心维护者进行审查，并可能将其转为退休状态。核心维护者应该尽早告知可用性下降的情况。

<a id="stepping-down" />
### 下台

您可以出于任何原因辞去任何职务。告诉与您一起工作的工作组负责人、IG 协调员、维护者或核心维护者，移交未完成的工作，并转为荣休状态。

<a id="emeritus-status" />
### 荣誉退休身份

荣誉职位持有者在 [`MAINTAINERS.md`](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/MAINTAINERS.md) 和发行说明中保留其认可，并且不承担任何职责或特权。

<a id="removal" />
### 移除

经过适当审查后，如果违反行为准则或持续不参与，可能会撤销角色。
