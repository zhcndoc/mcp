## 工作组类型

**工作组**

<a id="mission-statement" />
## 使命声明

传输工作组发展了 MCP 传输绑定和传输相邻
协议架构，因此实现保持可互操作性、可扩展性、可靠性、
并且易于跨本地和远程部署操作。工作组负责制定运输
提案、SEP、实施证据和指南。的
[工作组存储库](https://github.com/modelcontextprotocol/transports-wg)
维持工作组当前的技术重点、提案策略和支持细节
在这些界限之内。

<a id="scope" />
## 范围

<a id="in-scope" />
### 范围内

- **传输绑定**：成帧、交付、请求和信封元数据，
  取消和终止、连接生命周期、向后兼容性，以及
  现有和未来 MCP 传输的行为。目前的规格
  [运输概述](/specification/draft/basic/transports)定义边界
  传输绑定和核心协议语义之间的关系。
- **可扩展性和可靠性**：传输级连接管理、资源
  效率、多路复用、负载分配、错误处理、重新连接、
  恢复，以及由绑定提供的交付和订购保证。
- **传输相邻协议架构**：协议范围的消息流问题
  可扩展、可互操作的绑定所需，包括请求关联，
  每个请求的元数据、无状态操作以及从遗留初始化的迁移
  和传输会话模型。
- **运输安全**：装订和信封安全要求，例如来源地
  验证、TLS、mTLS 和证书处理，与安全 IG 协调。
  凭证传输与 Auth IG 协调。
- **验证和指导**：参考实现、实验、实现
  评估提案和帮助实施者所需的证据和文件
  采用商定的运输行为。支持材料在上游维护
  [提案目录](https://github.com/modelcontextprotocol/transports-wg/tree/main/proposals)。
  工作组为一致性测试提供传输场景和要求
  项目，其维护者拥有一致性套件。
- **跨领域协调**：其他 MCP 拥有的工作的运输影响
  组，而不拥有其应用程序层功能的所有权。

上游[使命宣言](https://github.com/modelcontextprotocol/transports-wg#mission)
提供支持背景，但不能扩大本章程的范围。

<a id="out-of-scope" />
### 范围外

- MCP 原语的应用层行为，例如 tools、resources、prompts、tasks、agents 或 events，包括应用状态、应用会话含义、任务生命周期以及事件或订阅语义。工作组会在这些功能依赖绑定或消息流行为时进行协调
- 特定领域的扩展以及特定实现的产品或业务关注点
- 与传输无关的 SDK API 和实现细节
- 授权协议机制、凭据和令牌语义、应用身份以及授权策略。工作组与相关工作组协调绑定如何承载约定的授权数据
- MCP 一致性测试套件的所有权。工作组与其维护者协调，贡献传输要求和场景

<a id="related-groups" />
### 相关工作组

- **[SDK WG](/community/working-groups/sdk)**：官方 SDK 实现传输
  变化；该小组就可行性、参考实施和
  推出顺序。
- **[任务和事件工作组](/community/working-groups/tasks-events)**：任务和
  事件工作组拥有任务和持久执行力；这些小组协调这些
  取决于多往返请求、请求关联、无状态操作，或者
  绑定行为。事件回调、订阅和应用程序级传递
  语义由该组拥有； Transports 拥有绑定特定的运输和
  保证。
- **[Auth IG](/community/interest-groups/auth)** 和
  **[Security IG](/community/interest-groups/security)**：各团体协调
  凭证携带和传输线路安全，同时授权机制和
  各个 IG 仍存在更广泛的安全要求。

<a id="operations" />
## 运作方式

工作组每周定期举行会议，当前时间和加入详情列于[meet.modelcontextprotocol.io](https://meet.modelcontextprotocol.io)。议题在[MCP Discord](https://discord.gg/6CSzBmMkjX)的 `#transports-wg` 频道中异步讨论。

工作遵循问题优先的工作流程：

1. 在[工作组仓库](https://github.com/modelcontextprotocol/transports-wg)中创建核心问题陈述，使工作组就问题及其要求达成一致
2. 与其他感兴趣的参与者合作定义解决方案
3. 审查并迭代解决方案，以回应工作组反馈
4. 工作组根据其决策流程达成共识后，通过[SEP 流程](/community/sep-guidelines)向 Core Maintainers 提交该解决方案作为 SEP

<a id="success-criteria" />
### 成功标准

- 已采用的与传输无关的协议行为在不同传输之间保持一致，同时绑定特定的差异得到明确说明，并通过实现证据和适用的一致性场景进行验证
- 影响官方 SDK 的传输变更与 SDK WG 协调，并具有清晰的实现指导
- 决策、提案状态和支持性理由持续在工作组仓库中公开可查，或提供从工作组仓库访问这些信息的链接
