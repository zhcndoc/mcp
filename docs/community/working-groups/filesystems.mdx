## 工作组类型

**工作组**

<a id="mission-statement" />
## 使命声明

文件系统工作组的存在是为了使 MCP 资源与通用文件系统语义保持一致，以便 MCP 客户端能够
一个用于跨源发现、检索和修改文件系统型资源的界面，并且可以这样做
高效。代理平台正在向模型提供服务作为文件系统，并且资源已经
在 [`file://` 方案下通过 URI 寻址内容，该规范将其定义为标识“行为类似的资源”
文件系统"](/specification/draft/server/resources#common-uri-schemes)。工作组将确定哪个文件系统
语义适合 MCP 并生成一个或多个扩展跟踪 SEP，将这些语义一致地应用于资源。

<a id="scope" />
## 范围

<a id="in-scope" />
### 范围内

- **规范工作**：一个或多个扩展跟踪定义资源操作的 SEP，涵盖：
  1. **范围列表和目录遍历。** 研究范围为 URI 的层次结构感知列表，包括
     枚举 URI 下面一级的操作，类似于 `readdir`，遍历整个子树，以及如何
     两者都与现有的扁平 `resources/list` 操作相关。
  2. **服务器端搜索。** 研究服务器评估的搜索和全局匹配，以便客户端可以找到内容
     无需列出和阅读所有资源。这超出了描述服务器 URI 的资源模板的范围
     接受。与范围列表和遍历一起，这涵盖了客户端如何发现服务器上的内容。
  3. **读取语义。** 研究哪种文件系统读取语义适合 MCP，包括批量读取以下文件系统中的多个 URI
     一个请求以及协议是否可以支持 `seek` 操作。
  4. **写入和元数据操作。** 定义创建、更新、删除和应答的元数据读取 (`stat`)
     一个 URI 的存在、大小和最后修改时间，无需获取正文。
  5. **乐观并发控制。** 指定两个写入器如何避免丢失更新，以及客户端如何创建更新
     在“缺席时创建”前提下的资源。
  6. **键入的错误。** 定义资源操作的错误，例如未找到、已存在、前提条件失败且
     权限被拒绝，因此客户端在服务器之间以相同的方式处理故障。目前缺少资源
     返回通用 `-32602`（无效参数）。
  7. **更改通知和缓存。** 指定文件系统操作如何与
     `notifications/resources/updated`、生存时间和缓存范围字段 `ttlMs` 和 `cacheScope` 以及
     `lastModified` 注释。
- **跨领域关注点**：协调将该原语扩展为一个连贯设计的提案。
  [SEP-2571，代理协调的资源提交](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2571)
  提出`resources/create`和`resources/delete`。
  [SEP-2532，用于二进制内容交付的资源流](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2532)
  建议`resources/stream`。
  [SEP-1708，MCP 客户端代理的文件系统访问](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1708)
  提出了与 Resources 并存的 `files/*` 方法系列，并于 2026 年 1 月 23 日关闭。
- **文档**：记录规范中采用的文件系统语义，并为服务器作者提供指导
  在资源操作和基于工具的操作之间进行选择。

<a id="out-of-scope" />
### 范围外

- 并行的 `files/*` 原语位于资源旁边。工作组扩展了现有的资源原语。
- POSIX 或其他操作系统的文件系统 API 的完整映射。工作组将选择适合的语义
  客户端-服务器协议并记录任何排除的理由。
- 主机端沙箱和本地磁盘语义。工作组标准化了客户端和服务器的有线格式。怎样当主持人
  将资源具体化到模型的文件系统中仍然是主机关注的问题。
- 文件系统操作的授权策略，超出说明现有 MCP 授权规范的位置
  适用。

<a id="related-groups" />
### 相关工作组

- **文件上传工作组。** 两个组都将内容传输到服务器。需要对面向上传的流程进行协调
  结束并开始资源写入操作。发现、搜索、元数据和小型内联写入不依赖于
  大内容传输，并且可以独立进行。工具已经返回资源链接，因此组
  还应该就接受文件的工具输入是否可以引用资源达成一致。
- **[MCP WG 的技能](/community/working-groups/skills-over-mcp).** 已发布
  [技能扩展](/extensions/skills/overview) 使用资源进行文件读取并定义可选的目录读取。
  它不依赖于文件系统写操作；协调影响技能的未来资源运营。
- **代理 IG。** 多代理和作业编排系统是共享文件系统语义的激励消费者。

<a id="success-criteria" />
### 成功标准

- 一个或多个接受的扩展跟踪定义范围列表和目录遍历、服务器端搜索和
  支持的读取、写入和元数据语义，包括批量读取。接受的作品必须记录工作组的
  关于`seek`的结论，定义乐观并发控制机制和一组类型错误，并指定
  与 `notifications/resources/updated`、`ttlMs`、`cacheScope` 和 `lastModified` 相互作用。
- 此空间中的每个提案均已解决。 SEP-2571 和 SEP-2532 在撰写本文时处于打开状态，并且每个最终都应折叠起来
  纳入、取代或明确界定范围。
- 至少两个第 1 层 SDK 中的参考实现。
- 两个独立的服务器实现针对公共客户端执行所采用的文件系统操作。
