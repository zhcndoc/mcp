## 工作组类型

**工作组**

## 使命声明

文件系统工作组旨在使 MCP Resources 具备双向能力，从而让智能体能够将结果写回它读取输入的服务器。智能体平台正逐渐将服务以文件系统的形式呈现给模型，而 Resources 已经通过 URI 处理内容，其中 [`file://` 方案由规范定义为用于标识“行为类似文件系统的资源”](/specification/draft/server/resources#common-uri-schemes)。目前，Resources 仅覆盖读取方向。该工作组将制定一份 Extensions Track SEP，涵盖写入操作、乐观并发控制，以及写入操作与变更通知和缓存之间的交互。

## 范围

### 范围内

- **规范工作**：一份暂定标题为 Resources 的文件系统操作的 Extensions Track SEP，涵盖：
  1. **操作**。定义创建、更新、删除以及元数据读取（`stat`），用于在不获取正文的情况下回答单个 URI 的存在性、大小和最后修改时间。
  2. **乐观并发控制**。规定两个写入者如何避免更新丢失，以及客户端如何在仅当不存在的前提条件下创建资源。
  3. **变更通知和缓存**。规定写入操作如何与 `notifications/resources/updated`、生存时间和缓存范围字段 `ttlMs` 与 `cacheScope`，以及 `lastModified` 注解交互。
- **跨领域关注点**：协调将这一原语扩展为统一连贯设计的提案。[SEP-2571，面向智能体协调的资源提交](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2571) 提议使用 `resources/create` 和 `resources/delete`。[SEP-2532，二进制内容交付的资源流式传输](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2532) 提议使用 `resources/stream`。[SEP-1708，MCP 客户端代理的文件系统访问](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1708) 曾提议使用与 Resources 并列的 `files/*` 方法族，并于 2026 年 1 月 23 日关闭。
- **文档**：在规范中记录新操作，并为服务器作者提供关于如何在资源写入路径和基于工具的路径之间进行选择的指导。

### 范围外

- 与 Resources 并列的另一套 `files/*` 原语。该工作组扩展现有的 Resources 原语。
- 主机端沙箱和本地磁盘语义。该工作组标准化客户端与服务器之间的线路格式。主机如何将资源具体化为供模型使用的文件系统仍属于主机关注事项。
- 写入授权策略，但需说明现有 MCP 授权规范适用的位置。

### 相关工作组

- **文件上传工作组**。两个工作组都会向服务器传输内容。需要协调上传导向的流程在哪里结束，以及资源写入操作从哪里开始。
- **MCP 技能工作组**。文件系统依赖（包括关于写入访问权限的问题）是 2026 年 3 月 24 日办公时间会议上的议题，仍有待解决。
- **智能体工作组**。多智能体和作业编排系统是共享写入路径的主要使用者。

### 成功标准

- 一份已接受的 Extensions Track SEP，涵盖创建、更新、删除和 `stat`，并定义乐观并发控制机制，规定其与 `notifications/resources/updated`、`ttlMs`、`cacheScope` 和 `lastModified` 的交互。
- 该领域的每项提案都得到解决。撰写本文时，SEP-2571 和 SEP-2532 仍处于开放状态，最终应当被纳入、取代，或明确排除在范围之外。
- 至少两个 Tier 1 SDK 中提供参考实现。
- 两个独立的服务器实现通过通用客户端使用写入路径。
