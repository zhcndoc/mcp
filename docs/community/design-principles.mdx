---
title: 设计原则
description: 指导模型上下文协议开发的核心设计原则。
---

这些原则指导我们如何评估协议提案、权衡权衡和发展 MCP。它们适用于[规范增强提案](/community/sep-guidelines) (SEP) 和[扩展](/extensions/overview)，并且与规范的[架构设计原则](/specification/latest/architecture#design-principles) 不同，后者描述了如何构建服务器和客户端。核心维护者在接受或拒绝 SEP 时引用它们。违背原则的提案应该这样说并说明原因。当两个原则发生冲突时，它们会相互权衡，而不是排名。

<a id="convergence-over-choice" />
## 收敛优于选择

MCP 中的问题应该有一种解决方法。我们不支持破坏生态系统的多种方法，而是选择一条精心设计的路径，预先接受更艰难的决策，以提供更具凝聚力的协议。

[扩展](/extensions/overview) 是检验收敛性的地方；规范则是承诺收敛性的地方。

<a id="composability-over-specificity" />
## 组合性优于特异性

MCP 提供基本原语：资源、工具和提示。我们不会为可以从这些现有构建块构建的用例添加协议功能。这使得表面积较小且实现简单。 [MCP 应用程序](/extensions/apps/overview) 和 [任务](/extensions/tasks/overview) 等扩展可捕获出现的模式。

<a id="interoperability-over-optimization" />
## 互操作性优于优化

MCP 运行在复杂程度各不相同的客户端、服务器和模型之间。我们倾向于支持优雅降级的功能，而不是那些仅当每个参与者能力相同时才有效的功能。能力协商使这一点具体化：参与者声明他们支持什么，协议据此适应而不是假设。

<a id="stability-over-velocity" />
## 稳定性优于速度

添加到像 MCP 这样广泛采用的协议很容易。从中删除几乎是不可能的。每一次添加都是永久的承诺，也是客户实施者支持的成本。我们谨慎地行动，知道今天的“不”会让大门敞开，而“是”则永远关闭它。我们优化数十年，而不是几个季度。当发生删除时，遵循[功能生命周期和弃用](/community/feature-lifecycle)。

<a id="capability-over-compensation" />
## 能力优于补偿

模型的改进速度快于协议的发展速度。我们避免添加永久性结构来解决可能是暂时的限制：限制消失，但复杂性仍然存在。

这并不是忽视当前现实的许可。较弱模型依赖而较强模型忽略的可选上下文没有任何成本。但是，当一个提案存在主要是因为当前模型没有它就难以运行时，我们会问在他们能够摆脱这个负担之前，模型是否已经不再需要它了。

<a id="demonstration-over-deliberation" />
## 演示优于审议

MCP 重视实际应用胜过理论争论，重视实际使用证据胜过假设性争论。我们鼓励贡献者制作原型而不是由委员会设计。 SEP 需要一个有效的[原型](/community/sep-guidelines#prototype-requirements) 才能被接受。

<a id="pragmatism-over-purity" />
## 实用主义优于纯粹性

MCP 为了采用率和可用性做出务实的权衡。我们不会以牺牲现实世界中的实用性为代价去追求理论上的优雅。当一个“正确”的设计给实现者带来摩擦时，我们会考虑“足够好”的设计是否能更好地服务于生态系统。这意味着接受一些不一致、一些历史偶然性，以及一些事后看来我们可能会做出不同选择的决策。

<a id="standardization-over-innovation" />
## 标准化优于创新

MCP 对已被证明有价值的模式进行了标准化。我们寻找适用于多种实现的约定并将其编纂出来，而不是发明新的范例并希望它们会被采用。新模式最好首先在[扩展](/extensions/overview)中尝试。
