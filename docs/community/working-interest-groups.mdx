本页列出 MCP 项目的工作组和兴趣组，说明如何加入或创建小组，并汇总适用于所有小组的运作规则。这些规则由规范增强提案（SEP）[SEP-2149](/seps/2149) 采纳。小组章程不得覆盖这些规则；修改规则需要提交流程类 SEP。参与小组工作不要求先成为成员，但 [SEP](/community/sep-guidelines) 必须先与相关工作组进行[讨论](/community/sep-guidelines#before-you-write)，并在拉取请求[标记为可供审查](/community/sep-guidelines#workflow)前获得赞助。你可以按自己的时间安排参加任意多个小组。

<a id="working-groups-and-interest-groups" />
## 工作组和兴趣小组

| | 工作组 | 兴趣组 |
| --- | --- | --- |
| 目的 | 制定具体方案 | 发现并讨论问题 |
| 产出 | SEP、参考实现，或对项目（例如 Inspector、Registry 或 SDK）的管理 | 问题陈述、用例、建议，以及对工作组和 SEP 的意见 |
| 决策 | 对范围内事项作出有约束力的决定：先寻求宽松共识，再投票，必要时升级 | 通过宽松共识形成不具约束力的建议 |
| 负责人 | 工作组负责人 | 兴趣组召集人 |
| 持续时间 | 持续至交付成果完成 | 主题仍相关时持续运作 |
| 示例 | [Transports](/community/working-groups/transports) | [Security](/community/interest-groups/security) |

通常由兴趣组提出问题，再由工作组推进解决方案。负责的工作组可以已经存在，也可以由兴趣组通过[组建小组](#forming-a-group)流程新建；后续 SEP 由该工作组赞助。

<a id="joining-a-group" />
## 加入小组

加入小组章程中列出的 Discord 频道（[沟通方式](/community/communication#discord)说明了频道命名约定）。参加 [meet.modelcontextprotocol.io](https://meet.modelcontextprotocol.io) 上列出的小组会议，并留意议程和会议记录（参阅[会议和频道](#meetings-and-channels)）。主动记录会议、准备议程或协助主持，是最快的参与方式。在 SEP 讨论中分享用例，并在准备就绪后承担工作组的交付事项。

如需列为参与者，请联系小组负责人。工作组成员资格按[参与级别](#participation-levels)中的提名流程确定。成员名单维护在 [access 仓库](https://github.com/modelcontextprotocol/access)，并据此配置 GitHub 团队成员资格和 Discord 角色。每次小组会议均适用[反垄断政策](/community/antitrust)。

<a id="leadership" />
## 领导力

每个小组都有一名或多名负责人；兴趣组中的负责人称为召集人。负责人或召集人至少须达到[成员](/community/contributor-ladder#member)级别，并持续参与小组职责范围内的工作。他们须能够跨组织协调合作、公平地呈现不同观点，并负责小组日常运作。对工作组负责人而言，这通常意味着每周投入 2 至 3 小时。小组及其负责人须由至少两名核心维护者或一名首席维护者赞助。

每位领导和协调员必须：
- 在[会议和渠道](#meetings-and-channels)下安排和召开定期会议
- 与参与者制定议程并提前发布
- 确保会议记录已发布
- 保持章程和其他团体文件的最新状态
- 保持[访问存储库](https://github.com/modelcontextprotocol/access)中的成员列表和访问列表为最新
- 招募并保留跨组织和观点的广泛成员
工作组负责人还必须：
- 通过 [SEP 流程](/community/sep-guidelines) 推动小组提案得到解决
- 对小组范围内的 SEP 进行分流；关闭不符合路线图的 SEP 时，在拉取请求中书面说明理由。作者可以向核心维护者提出申诉。
- 将受阻的决策上报给核心维护人员，并提供清晰的背景信息
- 保持小组的路线图（章程的活动工作项目）最新并将其输入[项目路线图](/development/roadmap)
- 定期与一名或多名核心维护者检查团队的总体方向
- 在[报告](#reporting)下发布季度更新
领导小组不要求具备维护者身份，并可作为晋升为[维护者](/community/contributor-ladder#maintainer)的经历。尚未成为维护者的负责人或召集人会与维护者协作处理合并决定。领导权限涵盖小组运作，不包括规范批准。工作组负责人可以为本组范围内的提案[提供 SEP 赞助](/community/sep-guidelines#sponsors)。

<a id="participation-levels" />
## 参与级别

| 级别 | 说明 | 权限 |
| --- | --- | --- |
| 观察者 | 对小组工作感兴趣的人 | 可旁听会议并有限参与讨论 |
| 参与者 | 积极参与小组讨论的人 | 可提出议程事项并参与异步投票 |
| 工作组成员 | 持续贡献且具备相关专业知识的人 | 计入法定人数（仅适用于工作组） |
| 负责人/召集人 | 负责小组日常运作 | 设置议程、主持讨论并按需升级事项 |

工作组成员是小组层面的参与级别，与项目范围的[成员](/community/contributor-ladder#member)角色不同：一个人可以不是项目成员，但成为工作组成员；反之亦然。兴趣组通常由观察者、参与者和召集人协作。如果兴趣组需要进行正式决策，也可以采用工作组成员级别。

在工作组或已采用此级别的兴趣组中，成为工作组成员须满足三项条件：持续参与至少 3 个月，并贡献代码、规范文本、审查意见或文档；由现有工作组成员或负责人提名；提名公布后 7 天内未遭负责人、核心维护者或主要维护者反对。成员须在小组名单中列出姓名、组织和 Discord 用户名。连续 3 个月未参与的工作组成员会转为荣誉成员；恢复参与后可重新成为正式成员。

<a id="making-decisions" />
## 做出决定

工作组按以下三个步骤，对其职责范围内的事项作出有约束力的决定；只有前一步无法解决时，才进入下一步。

1. **宽松共识。** 提案须公布明确的评论截止时间：次要事项至少 5 天，重要事项至少 10 天。未提出异议视为同意。任何工作组成员都可以提交书面阻止意见，但必须同时提出替代方案或明确的解决条件。截止时间前无人阻止，提案即获通过。
2. **正式投票。** 工作组成员在宽松共识阶段提出阻止意见后，或负责人、至少三名工作组成员要求投票时，发起正式投票。法定人数为活跃工作组成员的 50%。日常事项由简单多数通过；范围变更须获得三分之二多数。除非核心维护者明确说明其意见具有约束力，否则核心维护者的反馈仅作建议。每次投票都须记录理由。
3. **升级处理。** 未达到法定人数、提案未获通过或结果存在争议时，由负责人按照[升级流程](#escalation)提交核心维护者处理。

兴趣组通过宽松共识开展工作，产出不具约束力。采用工作组成员级别的兴趣组可以使用上述步骤进行内部决策。

每个工作组的章程都通过「权限与决策权」表，记录该组可自行决定的事项。该表随章程一并批准；之后的任何修改都遵循[修改或撤销小组](#amending-or-retiring-a-group)流程。

<a id="escalation" />
## 升级

通用升级流程和响应时限见[贡献者阶梯](/community/contributor-ladder#escalation)。

小组应先自行解决职责范围内的技术和设计分歧，再请核心维护者介入：工作组遵循[决策流程](#making-decisions)，兴趣组召集人寻求宽松共识。以下问题应直接提交核心维护者：职责范围争议、小组决策权限争议、跨组冲突、行为准则或行为问题，以及成员资格或参与争议。

收到升级事项后，核心维护者团队会指定一名成员处理并向小组反馈；该成员应避免与相关方存在组织上的从属关系。该核心维护者可以给出有约束力的指导、要求补充信息，或建议由核心维护者团队共同审议。升级事项应在 5 个工作日内收到初步回复。

<a id="meetings-and-channels" />
## 会议和渠道

各小组负责人自行设定会议频率、形式和时长，没有统一的固定节奏。每次小组会议都必须：
- 向所有社区参与者开放，不得举行闭门或仅限组织内部的会议。
- 至少提前 7 天发布在 [meet.modelcontextprotocol.io](https://meet.modelcontextprotocol.io) 上。
- 提供公开议程；会议前在 [GitHub 会议记录讨论区](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/)发布议程或其链接。
- 在 48 小时内将会议记录发布到同一讨论串。
- 仅使用官方 Google Meet 转录作为自动记录；根据[行为准则](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/CODE_OF_CONDUCT.md#community-meetings)，不得使用第三方 AI 记录工具或会议机器人。
- 遵循[行为准则](/community/policies#code-of-conduct)和[反垄断政策](/community/antitrust)。会议行为章节要求提供议程和会议记录。
- 从议程链接到[项目政策](/community/policies)。

负责人应邀请工作组成员和参与者协助准备议程、记录会议和主持讨论。

每个小组都有一个 Discord 频道（命名方式见[沟通方式](/community/communication#discord)），用于快速提问和协调；参与者应尽力及时回复。较长的技术讨论应转到 [GitHub Discussions](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/)，并每周分流一次。小组也可以申请独立的讨论类别。负责人会获得管理这些频道和讨论所需的权限。

<a id="reporting" />
## 报告

每个工作组须在 1 月底、4 月、7 月和 10 月发布季度更新，作为其 GitHub Discussions 类别中的一份文档。更新应涵盖交付进度、受阻工作和升级事项、成员变动、下一阶段优先事项及资源需求。核心维护者可以在会议上讨论这些更新。兴趣组没有定期报告要求，但应保持章程和成员名单为最新状态。

<a id="forming-a-group" />
## 组建小组

<a id="working-group" />
### 工作组

当某个得到广泛认可的问题需要协调推进时，可以成立工作组。事先在兴趣组讨论会有所帮助，但并非必需。如果已有明确的交付目标，也可以直接提议成立工作组。新小组及其负责人须获得[领导安排](#leadership)中规定的赞助；请在最相关的 Discord 频道或 `#wg-ig-group-creation` 中提出申请。获得赞助后，提议者按照[提交章程](/community/charter-template#submitting-a-charter)中的说明提交章程。工作组负责人批准初始成员名单。

<a id="interest-group" />
### 兴趣小组

在 [Discord](https://discord.gg/6CSzBmMkjX) 的 `#wg-ig-group-creation` 频道填写创建模板。核心维护者会审查提案；兴趣组及其召集人也须获得相同的赞助。获得赞助后，召集人组织兴趣组，并按相同方式提交章程，文件存放在 `docs/community/interest-groups/` 下。

<a id="amending-or-retiring-a-group" />
## 修改或撤销一个组

小组负责人、召集人或核心维护者可以提出章程变更；变更须经核心维护者批准，并记录在章程的变更日志中。

工作组负责人或核心维护者可以提出有理由的退休建议；经核心维护者或主要维护者批准后，小组即可退休。工作组完成所有计划交付成果，或长期没有活跃工作时，也可以退休。核心维护者或主要维护者可以关闭不再活跃或已无必要的兴趣组。

无论哪种情况，小组文档都会归档，其频道也会标记为非活跃。
