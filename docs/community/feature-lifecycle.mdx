<a id="scope" />
## 适用范围

本策略适用于 MCP 核心规范的**功能**：协议消息、能力、传输、模式类型，以及规范性的行为要求。规范文档本身的修订生命周期（Draft、Current、Final）定义于 [版本控制指南](/docs/learn/versioning)。

<a id="feature-states" />
## 功能状态

一个规范功能恰好处于以下三种状态之一：

| 状态           | 含义                                                                                                                                                         | 实现者预期                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| **Active**     | 该功能属于当前规范修订的一部分。                                                                                                                               | 按该功能的规范性要求实现。                                                                                               |
| **Deprecated** | 该功能仍保留在规范中，但已计划移除。迁移路径已文档化（见下文）。                                                                                               | 新实现不应采用该功能。现有实现应在最早移除日期之前完成迁移。                                                             |

<a id="deprecating-a-feature" />
## 弃用一个功能

在以下情况下，可以提议弃用某个功能：

- 它已被涵盖相同用例的另一个功能所取代，
- 它带来了无法避免的安全、隐私或互操作性风险
  就地缓解，
- 生态系统遥测或 SDK 维护者共识表明采用率可以忽略不计
  相对于其维护成本，
- 核心维护者认为出于任何其他原因是适当的。
弃用需要 SEP（请参阅 [SEP 指南](/community/sep-guidelines)）。

弃用 SEP 必须：
1. 通过名称识别功能并链接到 `schema.ts` 中的定义
   （如果适用）和规范文章。
2. 说明针对上述标准的理由。
3. 记录迁移路径，或明确说明不需要。如果
   迁移路径命名替换功能，该功能必须处于活动状态
   在弃用生效的修订中；更换和
   弃用可能会出现在同一修订版中。
4. 指定**最小弃用窗口**：至少月数
   十二，该功能必须保持弃用状态。该功能**最早
   删除**是作为当前版本发布的第一个规范修订版或
   窗口期过后。

当弃用 SEP 被接受时，其作者会进行以下更改
SEP 拉取请求中的规范草案，并且发起人验证
在设置 `final` 之前（请参阅
[SEP指南](/community/sep-guidelines#workflow)):
- 将 `@deprecated` JSDoc 标签添加到 `schema.ts` 中的功能条目，
  引用弃用 SEP 以及其中弃用的修订版
  生效。
- 添加弃用通知，其中包含与该功能相同的信息
  规范散文。
- 在该修订版的 `changelog.mdx` 下记录弃用信息
  “已弃用”标题。 “已弃用”和“已删除”是常设变更日志
  与主要/次要/其他一起的标题。
- 在[已弃用的注册表](#the-deprecated-registry) 中列出该功能
  其弃用 SEP、其被弃用的修订版、其
  迁移路径及其最早的移除。

当包含这些编辑的修订版本被弃用时，该功能将被弃用。

作为当前版本发布（请参阅[版本控制指南](/docs/learn/versioning)），并且
最小弃用窗口是从该版本开始计算的，而不是从发布之日开始计算的
9月进入决赛。

[SEP-2577](/seps/2577) 是弃用 SEP 的有效示例。

<a id="tier-1-sdk-obligations" />
## Tier 1 SDK 义务

一旦某个功能变为“已弃用”的修订版本被发布为“当前”版本，
第 1 层 SDK：
- 必须在其下一个版本中，使用该语言的原生机制将对应 API 面标记为 deprecated（例如 Java 中的 `@Deprecated`、.NET 中的 `[Obsolete]`、TypeScript 中的 `@deprecated` JSDoc、Go 中的 `Deprecated:` 文档约定），并在机制允许时引用弃用 SEP 以及最早移除日期。
- 当使用了已弃用功能时，应使用该语言惯用的机制发出运行时警告（例如 Python 的 `DeprecationWarning`、Node.js 的 `process.emitWarning`，或可配置的日志记录器）。

始终无法显示已弃用功能的第 1 层 SDK 受到影响
至 [等级降级](/community/sdk-tiers#tier-relegation)。

<a id="removing-a-feature" />
## 移除一个功能

在最短弃用窗口期满后，核心维护者可以删除
准备发布时的功能。删除记录在
`changelog.mdx` 在“已删除”标题下和
[注册表](#the-deprecated-registry)。对原始弃用的任何更改或
删除，例如延长或缩短时间
（[加急删除](#expedited-removal)）或将该功能恢复为活动状态
（[功能状态](#feature-states)），需要 SEP。可能会保留一个功能
无限期弃用。

<a id="expedited-removal" />
## 加速移除

当该功能出现问题时，十二个月的最短窗口可能会缩短
主动安全风险，意味着已发布安全性的漏洞
咨询或记录的野外利用，但没有就地利用
存在缓解措施。缩短窗口需要核心维护者的批准
根据[治理决策流程](/community/governance#decision-process)，
记录在弃用 SEP 中，或者该 SEP 之后出现的风险是
已经是最终版本，在引用它的简短快速删除 SEP 中。的
缩短的窗口必须在功能之间提供至少九十天的时间
已弃用并最早被删除。
